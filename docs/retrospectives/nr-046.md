## A picture diff at 300-frame checkpoints pointed at frame 1003, but the state had diverged at frame 2

**What happened.** The bead's recipe compares PNGs every 300 frames, and it placed the divergence at
frame 1003. I dumped CPU RAM at every NMI from both emulators instead: a Mesen2 Lua script on
`emu.eventType.nmi` and a temporary env-gated dump in NESER's NMI path. The first difference was at
NMI 2 (`$440`/`$441`, the game's per-port input reports). That led straight to the Vs. Zapper being
on the wrong port. Dumping at `startFrame` or `endFrame` did not work: the game spins an RNG in its
idle loop, so any mid-frame sample differs between the emulators. The NMI is the only synchronous
sampling point. Separately, a per-instruction trace (Mesen2 `callbackType.exec` plus a temporary
NESER log of PC, cycle and dot) found the second cause at frame 4 in one pass.
**Why.** Pictures show only what the game has drawn. The RAM had been different long before any of
it reached the screen.
**Cost.** One earlier session handed the bead back without a reproduction. This run took about an
hour to reach both causes once RAM was compared.
**Prevent by.** `scripts/reference_capture/README.md` should gain a section "Finding the first
divergent frame", with the NMI-synchronous RAM-dump Lua script and the exec-trace script used here.
Any "diverges from Mesen2 at frame N" bead should start with the RAM diff, not the picture diff.
**Seen before.** nr-0an and nr-2fw (drift first seen in pictures and traced to timing); neither
used a RAM diff.

## Mesen2 and NESdev disagree on NMI during a taken branch, and matching Mesen2 would have broken a spec-backed test

**What happened.** After the port fix, the demo still drifted from frame ~950. The cause was
NESER delaying an NMI that arrives during a taken same-page branch. NESdev's "CPU interrupts" page
describes that delay for all interrupts. Mesen2's `BranchRelative` delays only `_runIrq`, even
though its own comment says "IRQ/NMI". Copying Mesen2 made all 3600 NMIs and all 12 checkpoints
match, but changed Zap Ruder's X-tracking result from 7 to 8. The navigator chose to keep the
specification's behaviour.
**Why.** Mesen2 is the reference implementation, not the specification. The bead's acceptance
("same picture as Mesen2") assumed the two agree.
**Cost.** One navigator question, and an acceptance amendment.
**Prevent by.** The kept difference is now documented on `skip_interrupt_latch_this_cycle` in
`src/nes/cpu/cpu/mod.rs`. A bead whose acceptance is Mesen2 frame parity should say, in its
acceptance, that a difference traced to Mesen2 departing from NESdev ends the bead rather than
failing it.
**Seen before.** nr-1le (Mesen2's wrong Vs. palette) and nr-2fw (Mesen2's PAL scanline).

## A Mesen2-parity bug hid that Vs. Duck Hunt could not be started at all

**What happened.** The bead was filed as "the attract demo diverges". The wrong Zapper port also
meant the gun's trigger never reached the game, so "AIM AND FIRE TO START GAME" could not be
answered. The review asked whether a player could still start the game, and the check showed it
had never been possible before.
**Why.** The sweep compares no-input runs, so it cannot see an input device that is wired wrong.
**Cost.** None beyond the review's question; the check took minutes.
**Prevent by.** For a game whose ROM-DB entry names an input device (Zapper, Vs. Zapper, Power Pad,
Arkanoid), a bead fixing its no-input divergence should also check that the device reaches the
game, with a short headless run that uses the device.
**Seen before.** none found.
